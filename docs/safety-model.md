# 安全模型与护栏

清理工具的价值取决于它**敢删什么**，更取决于它**绝不删什么**。agent-sweep 的安全性是结构性的，不依赖用户是否记得加参数。

## 三圈层

```
        ┌─────────────────────────────────────────────┐
        │  第 3 圈 · 永不清理（硬约束）                 │
        │  记忆 / 凭据 / MCP 注册 / 插件 / 活跃占用 /   │
        │  仅报告目标                                    │
        ├─────────────────────────────────────────────┤
        │  第 2 圈 · 需确认后清理                       │
        │  陈旧但仍含不确定性的会话数据                 │
        │  （需显式 --include-review）                  │
        ├─────────────────────────────────────────────┤
        │  第 1 圈 · 可安全清理                         │
        │  孤儿 worktree / 陈旧缓存 / 日志 / 缩略图     │
        │  （默认执行）                                  │
        └─────────────────────────────────────────────┘
```

圈层是**执行前的最后一道闸门**，独立于体积评分：一个 50 GB 的受保护对象永远不会因为「大」而进入可执行集合。

### 判定短路顺序

`classifyUnit()` 严格按以下顺序短路，先命中先决定：

| # | 条件 | 结果 |
| --- | --- | --- |
| 1 | 命中显式护栏（`neverDelete` / 全局保护路径 / 敏感文件名） | 第 3 圈 |
| 2 | 目标 `removable: false`（仅报告） | 第 3 圈 |
| 3 | 进程占用（打开文件 / lock PID 存活） | 第 3 圈 |
| 4 | 未超过 TTL | 保留 |
| 5 | 低于 `--min-size` | 保留 |
| 6 | 孤儿（worktree 主仓库缺失 / 宿主项目已删除） | 第 1 圈 |
| 7 | 缓存 / 日志 / 缩略图 | 第 1 圈 |
| 8 | 低风险陈旧对象 | 第 1 圈 |
| 9 | 其余陈旧对象 | 第 2 圈 |

进程占用是**硬性否决项**：命中即落第 3 圈，任何参数都无法覆盖。

## 护栏的两类来源

### 1. 全局保护路径（`GLOBAL_PROTECTED_PATHS`）

跨 harness 通用的治理资产，例如：

```
~/.claude.json                    ~/.claude/settings.json
~/.claude/plugins/**              ~/.claude/history.jsonl
~/.claude/projects/*/memory/**    ~/.codex/config.toml
~/.cursor/mcp.json                ~/.trae-cn/mcps/**
~/.trae-cn/memory/**              ~/.gemini/oauth_creds.json
~/.config/opencode/**             ~/.agents/**
```

### 2. 声明式护栏（harness `neverDelete`）

每份 harness 声明可以追加自己的保护路径，注册表加载时合并进同一个护栏集合，并标注来源（`harness-guard:<id>`）。

### 敏感文件名启发式

以下文件名会被视为敏感，只保护**单个文件**：

- `.env`、`.env.local`（但 `.env.example` / `.env.sample` / `.env.template` / `.env.dist` 等**模板不算**）
- 名称中含 `credential(s)` / `secret(s)` / `token(s)` / `apikey` / `password` / `oauth` / `auth` 的文件
- 固定资产名：`CLAUDE.md`、`AGENTS.md`、`.mcp.json`、`.clinerules`、`.cursorrules`、`.aider.conf.yml`、`.worktreeinclude`

## 目录级保护的精确性

一个容易踩的坑：**文件名启发式不能用于目录级包含判定**。

设想一个会话目录 `~/.claude/projects/-home-me-app/`，里面恰好有一份 `.env.example`。如果用文件名启发式去扫描子树，整个目录（可能 1.8 GB）会被误判为「包含受保护文件」而进入第 3 圈，导致真正的垃圾永远清不掉。

因此 `evaluateProtection()` 分两条通道：

| 通道 | 输入 | 使用的规则 |
| --- | --- | --- |
| 顶层判定 `matchGuard(absPath)` | 单元自身路径 | 显式护栏路径 **+** 固定资产名 **+** 敏感文件名 |
| 子树探测 `matchGuardDescendant()` | 后代路径 | **仅**显式护栏路径（注册表内声明） |

子树探测只认注册表里的显式路径，不认文件名启发式。这样「目录里有个 `.env.example`」不会冻结整个目录，而「目录里真的存在 `memory/` 或 `mcps/`」仍然会正确保护。

## 三层防线

1. **计划期**：圈层分类把危险对象排除在动作集合之外。
2. **执行前复检**：`verifyAction()` 对每个动作重新校验存在性、护栏与进程占用——防止计划过期导致误删。
3. **计划文件是不可信输入**：`clean --plan-file` 加载落盘计划时，动作会对照**当前**注册表重新过删除闸门——harness 或目标已降级为仅报告的，整份计划文件被拒绝（退出码 2），而不是信任文件里记录的圈层与权限。
4. **可还原**：默认移入回收站并写清单，`restore` 可回滚；只有显式 `--direct-delete --yes` 才是不可逆的。

## 非交互保护

`clean` 在没有 `--yes` 且 stdin 不是 TTY 时会**拒绝执行**并返回退出码 2，避免在 CI / 脚本里静默删数据。`trash empty` 同理。

## 刻意不做的事

- 不扫描项目仓库内部（`node_modules`、`dist` 等）——那属于项目自身的清理范畴。
- 不对「仅报告」harness 产生任何可执行动作，即使参数全开。
- 不提供「跳过护栏」的开关。护栏没有后门。
